# Agentic SDLC Orchestrator: URL Shortener

A runnable prototype that turns a requirement into a **reviewable engineering outcome** through a governed, stateful, non-linear agentic workflow. The orchestration layer is the product; the URL shortener is the system it builds, changes and validates.

**Stack:** Node.js >= 20, zero runtime dependencies (`node:test` for tests).

## Quick start
```bash
npm test                     # 51 tests: service, orchestrator, end-to-end scenarios
npm run demo:all             # runs all three scenarios (auto-approve DEMO mode)
node src/cli.js greenfield   # interactive: you approve each high-impact checkpoint
node src/cli.js greenfield --auto-approve --chaos   # add injected transient failures
npm start                    # run the reference URL shortener (PORT=3000, API_KEY=dev-key)
```
Each run writes to `runs/<scenario>-<timestamp>/`:
* `workspace/` the produced project (code, tests, OpenAPI, docs, ADRs, `docs/ENGINEERING_SUMMARY.md`)
* `evidence/` `audit.jsonl` (hash-chained), `metrics.json`, `lineage.json`, `run-state.json`, `workflow.mmd`, `RUN_REPORT.md`

## The three scenarios
| Scenario | Shows |
| --- | --- |
| `greenfield` | precise requirement -> 10-node DAG, parallel branches + sync, API contract and release approvals, generated project runs its own tests |
| `brownfield` | security bug in a legacy service: import-graph impact analysis, reproduce-red-first, naive patch rejected by gate -> bounded retry -> fallback strategy, blast-radius check |
| `ambiguous` | vague request -> ambiguity detection -> dynamic re-plan inserts a human clarification node -> mid-run stakeholder change invalidates and regenerates downstream work |

Details: [docs/SCENARIOS.md](docs/SCENARIOS.md).

## Orchestration capabilities
Explicit DAG with entry/exit gates | parallel paths with sync | versioned cross-stage context and decision lineage | human approval for high-impact nodes (enforced at graph build) | bounded retries, fallback, journaled rollback, safe-stop budgets and kill switch | policy guardrails (secrets, dangerous APIs, path traversal, dependency allow-list, command allow-list, change budget) | hash-chained audit log | reliability metrics (success rate, first-attempt rate, retries, rollbacks, fallbacks, MTTR, e2e latency, approvals) | dynamic re-planning on upstream change.

## Reference service API
| Method | Path | Auth |
| --- | --- | --- |
| POST | `/api/v1/links` `{url, customAlias?, ttlSeconds?}` | public, rate limited |
| GET | `/{code}` (302 / 404 / 410) | public |
| GET | `/api/v1/links/{code}` | `X-API-Key` |
| GET | `/api/v1/links/{code}/analytics` | `X-API-Key` |
| DELETE | `/api/v1/links/{code}` | `X-API-Key` |
| GET | `/healthz`, `/metrics` | public |

Env: `PORT`, `BASE_URL`, `DATA_FILE` (enables file persistence), `API_KEY` (required when `NODE_ENV=production`).

## Project layout
```

test/               service/ and orchestrator/
```

## Honest limitations
Agents are rule/template based (no LLM is called); orchestration is in-process with no crash-resume; `--auto-approve` is a demo bypass of real human review; the service is single-instance. See [docs/TESTING.md](docs/TESTING.md).
